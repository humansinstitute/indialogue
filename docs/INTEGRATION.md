# NStack integration

In Dialogue 1.3 connects to an existing NStack HTTPS origin through Tower's typed Flight Deck PG APIs. The client owns recording, local transcription, deterministic vocabulary and export; NStack owns workspace permissions, storage and channel delivery. No backend changes or storage-provider credentials are required.

Launch or foreground requests the existing PIN when an imported Nostr identity is locked. Unlock resumes eligible paused uploads. Continue locked allows recording and waits until the next foreground to prompt again. Menu → Identity provides identity management. On the capture screen choose Normal, Channel or Agent. Route setup discovers accessible workspaces and existing channels in every accessible scope, including DMs; it never joins or creates either. Normal retains the ordinary saved destination. Channel saves a channel without an agent mention. Agent requires a canonical checksum-valid directory npub, its matching label and a meaningful prompt. DM participant labels help name destinations but never become receiving-agent choices. The workspace-agents directory remains routing authority and its visibility/instruction flags are honored. The prompt is sent as an instruction, not executed by a local or cloud model.

The selected mode, destination, prompt, canonical recipient and conversation/thread identity are copied into the recording before microphone capture begins. Later setup changes cannot retarget that recording or a follow-up. Automatic delivery applies to recordings saved after enablement; its durable intent retains the same route while waiting for transcription. Final current review text receives deterministic vocabulary corrections before the export snapshot is created; the raw transcript is preserved locally and included in the transcript artifact, while unaccepted AI drafts remain local and are excluded from upload. Existing library entries require their explicit Upload button. Incomplete capture or export cannot be uploaded as complete.

Each immutable snapshot retains audio, full transcript JSON, raw/corrected text, prompt, capture metadata, SHA-256 checksums, destination, signer and stable client request ID. The message contains a bounded excerpt; the artifact contains the full text. A receiving-agent mention emits its visible Markdown tag and matching structured entry from the same value. An initial turn creates a new thread with a useful title. Respond copies the conversation route and posts with `thread_id`; kind 33358 signs that exact thread tag. Repeated turns retain the same conversation and retry with the same request/object IDs.

Reply refresh uses the typed effective-thread message API while the app is foregrounded and the matching identity is unlocked. A visible sent conversation checks immediately on activation/resume, then at a bounded 20-second interval until hidden, recording starts, the identity changes or the app leaves the foreground. One read is allowed at a time, repeated reply IDs are not republished, and manual Refresh Reply remains available. It does not scrape Flight Deck or poll in the background. The newest non-recorder message is shown as text. If it links an audio attachment, authorized `/storage/:id/content` bytes are played; otherwise iOS speech synthesis renders the visible text. Playback remains user-started and stoppable. Network failure leaves the sent recording and conversation IDs intact for the next bounded or explicit refresh. Android continues to use compatible optional route/thread fields, but its compact mode and reply UI are a follow-up rather than silent protocol divergence.

The decoder follows the typed message contract: JSON null deletion fields mean active, true tombstones and recorder-authored turns are skipped, fractional ISO timestamps and inherited provenance fields are accepted, and the endpoint's ascending cursor order determines the newest eligible reply. Malformed active rows produce a visible response error instead of being reported as an empty thread.

Storage preparation is private (`is_public:false`) and uses the workspace-owned PG route. Prepared object IDs are persisted before PUT. Presigned HTTPS upload streams a file without Nostr Authorization. The API fallback uses signed JSON base64 and is limited to 8 MiB to bound memory. Complete is followed by metadata read-back of `completed_at`, size and checksum. Byte counts accept nonnegative JSON integers and decimal integer strings, rejecting fractions, booleans, malformed values and overflow. Missing completion, invalid server metadata, mismatched remote integrity and changed local snapshots produce distinct errors; delivery never bypasses checks. Server checksums currently reflect client-declared lifecycle metadata, not an independent server byte digest. Signed API requests always use the configured HTTPS origin, including when proxy-generated descriptors advertise HTTP. Redirects are refused; advertised completion/content URLs cannot redirect authentication elsewhere.

Message instructions are Nostr kind 33358, binding the exact trimmed body/hash, workspace and channel, plus the thread for follow-ups. NIP-98 kind 27235 separately binds the URL, method and SHA-256 of the exact JSON bytes. The vault alone derives npub and signs using pinned [swift-secp256k1 0.23.2](https://github.com/21-DOT-DEV/swift-secp256k1/tree/0.23.2), backed by libsecp256k1. Existing AES-GCM/PBKDF2/Keychain vault format and PIN semantics are retained. Only public identity/events leave the vault.

Uploads require foreground, idle capture and an unlocked matching identity. Background retains the authenticated key only in the existing memory vault and cancels network work; foreground resumes paused jobs when the matching identity is still unlocked. Explicit Lock/removal clears authentication; a cold process launch requires PIN and never auto-decrypts. Failures are durable and require explicit retry, with the original snapshot/destination and client request ID. The recording’s Retry upload action also retries an existing failed snapshot without exporting again or adopting changed configuration. Already completed objects are validated and reused without another PUT or prepare. No timed retry loop runs. An uncertain prepare cannot safely allocate a second object: it stops with an explicit notice. Expired presigned URLs remain on the failed snapshot; the current backend has no upload-URL refresh route, so operator review may be required. Interrupted/ambiguous message responses retry the same request ID and attachment IDs. Configuration changes apply to future intents, not existing snapshots; another identity pauses mismatched jobs.

Menu → NStack uploads shows retained history, errors, Retry same snapshot and Cancel local delivery. Local deletion/cancellation cannot retract a remotely committed message or delete remote storage. Original audio and transfer snapshots are retained on failures. There is no uninterrupted background-upload promise and no automatic remote retention cleanup.

Discovery reads all accessible scopes, including the DM scope, and every channel page. Channel title/name fields are used directly; generated DM titles use available member and canonical agent labels, excluding the current signer. Membership labels do not confer agent routing authority. The directory's `agent_npub` takes precedence over presentation actor identities; hidden, archived or instruction-disabled entries are excluded. A successful empty directory and a failed/denied directory have separate visible statuses. Reopening saved setup restores its workspace/channel IDs and readable labels. When a mode has no saved route, setup derives the valid Tower origin, signer, workspace and app identity from another route in the same installation without persisting a migration: Channel asks for a channel, while Agent retains the accessible shared channel and asks for an agent. Existing routes, recordings and transfer snapshots remain unchanged until an explicit route save or new capture.

Discovery primarily uses the initial `/sync?limit=1` snapshot. Current Tower returns all visible scope/channel metadata on every sync page (up to 10,000 scopes and 10,000 channels per scope); sync cursors paginate channel message bundles, not these discovery arrays. The client reads metadata without walking unrelated message history. A metadata cap produces an actionable limit error.

If sync is unavailable, the client reads accessible scope/channel lists and unions `/me.visible.channels` to include directly granted channels. Scope/channel and `/me` lists cap at 200; the client requests 200 and follows scope/channel `next_cursor` when supplied. A full capped page without continuation is reported as incomplete. Fallback discovery visibly explains the missing complete snapshot, and independent directory results survive a channel failure. This client release does not change shared services or permissions.
