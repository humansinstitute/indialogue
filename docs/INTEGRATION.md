# NStack integration

Recorder 1.2 connects to an existing NStack HTTPS origin through Tower's typed Flight Deck PG APIs. The client owns recording, local transcription, deterministic vocabulary and export; NStack owns workspace permissions, storage and channel delivery. No backend changes or storage-provider credentials are required.

Open Menu → Identity to unlock the explicitly imported Nostr identity. Then open NStack, enter the HTTPS origin, discover accessible workspaces, choose a storage workspace and an existing message channel in any accessible scope (including DMs). Nothing joins or creates a workspace/channel. Optional agent routing requires a canonical checksum-valid npub and a label; DM participants are offered from channel discovery. The client requests the workspace-agents directory and honors visibility/instruction flags; a validated explicit field appears if the directory is unavailable or denied. A name alone never selects an agent. Save a meaningful custom prompt and explicitly enable automatic delivery if desired. The prompt is sent as an instruction, not executed by a local or cloud model.

Automatic delivery applies to recordings saved after enablement. A durable intent captures the destination at save time and waits for transcription. Final current review text receives deterministic vocabulary corrections before the export snapshot is created; the raw transcript is preserved locally and included in the transcript artifact, while unaccepted AI drafts remain local and are excluded from upload. Existing library entries require their explicit Upload button. Incomplete capture or export cannot be uploaded as complete.

Each immutable snapshot retains audio, full transcript JSON, raw/corrected text, prompt, capture metadata, SHA-256 checksums, destination, signer and stable client request ID. The message contains a bounded excerpt; the artifact contains the full text. A receiving-agent mention emits its visible Markdown tag and matching structured entry from the same value. Each recording starts a new thread with a useful title.

Storage preparation is private (`is_public:false`) and uses the workspace-owned PG route. Prepared object IDs are persisted before PUT. Presigned HTTPS upload streams a file without Nostr Authorization. The API fallback uses signed JSON base64 and is limited to 8 MiB to bound memory. Complete is followed by metadata read-back of `completed_at`, size and checksum. Server checksums currently reflect client-declared lifecycle metadata, not an independent server byte digest. Signed API requests always use the configured HTTPS origin, including when proxy-generated descriptors advertise HTTP. Redirects are refused; advertised completion/content URLs cannot redirect authentication elsewhere.

Message instructions are Nostr kind 33358, binding the exact trimmed body/hash, workspace and channel. NIP-98 kind 27235 separately binds the URL, method and SHA-256 of the exact JSON bytes. The vault alone derives npub and signs using pinned [swift-secp256k1 0.23.2](https://github.com/21-DOT-DEV/swift-secp256k1/tree/0.23.2), backed by libsecp256k1. Existing AES-GCM/PBKDF2/Keychain vault format and PIN semantics are retained. Only public identity/events leave the vault.

Uploads require foreground, idle capture and an unlocked matching identity. Background locks the vault and cancels network work; foreground plus unlock resumes paused jobs. Failures are durable and require explicit retry, with the original snapshot/destination and client request ID. No timed retry loop runs. An uncertain prepare cannot safely allocate a second object: it stops with an explicit notice. Expired presigned URLs remain on the failed snapshot; the current backend has no upload-URL refresh route, so operator review may be required. Interrupted/ambiguous message responses retry the same request ID and attachment IDs. Configuration changes apply to future intents, not existing snapshots; another identity pauses mismatched jobs.

Menu → NStack uploads shows retained history, errors, Retry same snapshot and Cancel local delivery. Local deletion/cancellation cannot retract a remotely committed message or delete remote storage. Original audio and transfer snapshots are retained on failures. There is no uninterrupted background-upload promise and no automatic remote retention cleanup.
